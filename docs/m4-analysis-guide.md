# M4-001 用户验证分析指南

状态：分析框架已冻结；尚无参与者数据。  
最后更新：2026-09-16

## 输入与完整性检查

每名参与者应有一份测试前记录、四份任务记录、观察表和一份测试后记录。任务数据来自应用下载 JSON 与 [结果模板](../pilot_results_template.json)。分析前检查：

1. `participant_id` 只使用 P01–P08，不含个人信息。
2. `task_id` 为 T1–T4；同一参与者与任务只有一个最终记录。
3. 核对 `completion_status`、任务用时、主持人提示和所选路线。
4. 缺失或损坏记录保留在分母说明中，不自行补值。
5. 将自由文本中的偶然身份信息删去后再归纳。

## 三层分析

结果模板中的 `selected_itinerary_id` 是参与者在页面提交的选择；`preferred_alternative_id` 只在参与者口头明确偏好另一条已展示路线时填写，用于发现操作结果与真实偏好的分歧。两者相同或没有替代方案时，后者保持 `null`。`confidence_rating_1_to_5` 表示对本次选择或拒绝的把握，不等于对数据或产品的信任。

### Evidence｜证据

可直接观察或由系统记录的事实，例如：

- 参与者比较了两张卡片后选择方案 A。
- 在“交通负担”处停顿 40 秒并展开航段详情。
- T4 将“样本内无解”解释为“现实没有航班”。
- 主持人提示一次后才找到必去目的地输入。
- 应用展示 5 个方案，任务用时 310 秒。

证据描述发生了什么，不推测动机。

### Opinion｜意见

参与者对体验的解释或评价，例如：

- “这个分数不知道差 5 分意味着什么。”
- 信任评分 3/5。
- 自述比平时开多个网站更省力。

意见是重要信号，但不能替代行为。记录原意和场景，不把单句评价扩展成全体结论。

### Decision｜决策

团队依据多条证据和预设门槛采取的下一步，例如：

- 先重写交通负担解释，再用相同任务复测。
- 理解与价值信号通过，进入少量人工真实报价验证。
- 多数用户理解后仍不需要组合发现，暂停扩大投入并重新定义目标用户。

每项决策必须列出支持证据、反例、样本限制和负责人；不能从一个意见直接跳到功能需求。

## 编码规则

### 任务完成状态

- `completed_independently`：未获主持人操作或解释提示，作出选择或明确拒绝。
- `completed_with_assistance`：提示后完成。
- `not_completed`：无法完成或退出。
- `technical_failure`：部署或记录故障阻止任务；不计入产品理解失败，但单列报告。

### 理解评分

对每名参与者按行为证据评分：

- 推荐类别：测试后能正确解释至少 3/4 类别。
- T3 取舍：至少说出一项具体收益和一项具体代价。
- T4 边界：明确说出结果只针对加载的模拟数据，并知道系统未自动放宽约束。

三项均通过才计为“理解通过”。不能只用参与者自评替代。

### 信任与有用性

- 信任信号要求评分 ≥4 且能指出至少一项仍需外部核对的信息。
- 有用性信号要求评分 ≥4 且选择一条继续核对路线，或基于具体理由明确拒绝全部路线。
- 选择默认第一名但不能解释理由，不计为有用性证据。

### 非直觉发现

同时满足：参与者表示路线原本未想到；能描述路线；愿意进一步核对。仅看到新路线但立即拒绝，不计入“愿意考虑”。

### 规划努力

报告每项任务的中位用时、范围、独立完成率、提示次数和常见回退点。测试前自述耗时及测试后“更快/相同/更慢”只作上下文。由于没有配对人工基线，不计算时间降低百分比，不作因果结论。

## 汇总表

每项指标同时报告分子、分母和人数，例如“4/6”，避免只写百分比。建议汇总：

自由文本按主题编码：推荐类别、费用口径、交通负担、偏好分、停留、无解、数据可信度、需要核对的信息、规划步骤。保留与主要模式相反的意见。

## 解释顺序

1. 先报告样本、完成度和技术故障。
2. 再报告观察行为和任务结果。
3. 然后报告评分与评论。
4. 对照冻结门槛，列出支持证据和反例。
5. 最后形成下一步决策；没有数据的维度保持“未评估”。

## 不允许的结论

在本轮结束后仍不能仅凭 5–8 人声称：产品市场契合、市场需求比例、真实机票节省、排序对所有用户正确、30% 规划时间降幅、真实报价覆盖充分或用户愿意付费。
