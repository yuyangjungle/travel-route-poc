# M1 可复现基准

状态：M1 基准保持不变；M2 真实搜索已在同一套场景上通过。  
最后更新：2026-09-16

## 目标与边界

为 M2 提供可核对的输入、反例和结果预期。M1 不实现优化器，也不枚举路线。

“见证行程”是人工明确列出的报价和访问序列。验证工具只回答这条行程是否满足约束，以及其费用、时间和评分是否符合手工预期。没有列出的行程仍可能存在；见证清单不是可行集或 Pareto 全集。

每个场景代表一个产品假设，并引用 [PRD](product/prd.md) 的 FR 和 A 编号。通过基准说明模型和校验器按预期工作，不说明用户已认可假设，也不说明真实票价可获得同样结果。

## 固定输入

| 文件 | 内容 |
| --- | --- |
| [manifest.json](../data/m1/manifest.json) | 数据版本、统一票价口径、标签与覆盖限制 |
| [airports.json](../data/m1/airports.json) | PVG、HGH、TWU、BKI、KUL、SGN、DPS、SIN、HKT，共 9 个机场 |
| [destinations.json](../data/m1/destinations.json) | SEMPORNA、KOTA、KL、SAIGON、BALI、PHUKET，共 6 个目的地 |
| [accesses.json](../data/m1/accesses.json) | 6 个接入映射；每方向固定 60 分钟、¥50 |
| [offers.json](../data/m1/offers.json) | 15 条固定单程报价，其中 2 条包含受保护联程 |
| [scoring.json](../data/m1/scoring.json) | score-v1 参数，不随运行变化 |
| [fixtures.lock.json](../benchmarks/fixtures.lock.json) | 上述 6 个数据文件与 20 个场景文件的内容哈希 |

数据覆盖声明为 2026-10-01 至 2026-10-31，但不是每天每条边都有报价。每个场景仅使用自身 `offer_ids` 指定的报价子集。目录、目的地规则和参数共享，以免一个案例的低价边污染另一个案例的证明。

所有报价、时刻、标签分、季节分和接驳均为人工编造的测试数值。月份评分统一为 100，用于隔离路线与时间因素，不能解释为全年适宜。机场标识和时区用于转换测试，不表示存在这些航班。

票价口径固定为：一名成人、CNY、含税、单件不超过 7kg/55×40×20cm 随身行李、无托运行李。这只是模拟共同口径，不是任何航司的政策。

## 关键手工推导

### B01：增加 KL

基线：PVG → TWU（访问 SEMPORNA）→ PVG。10/03 起飞、10/14 返回。

- 机票：180000 + 180000 = 360000 分。
- 交通：360 + 360 + 60 + 60 = 840 分钟。
- 地面接驳：5000 + 5000 = 10000 分，单列，不扣机票预算。
- SEMPORNA：10/03 15:00 抵达目的地，10/14 09:00 离开，11 夜。
- 有效游玩：首日 300 + 中间 10×720 + 末日 60 = 7560 分钟。
- B = 840/60 + 2×2 = 18；E = 100；综合分 50.551948。

增加 KL：PVG → TWU（SEMPORNA）→ KUL（KL）→ HGH。

- 机票：180000 + 30000 + 70000 = 280000 分，减少 80000 分。
- 交通：360 + 180 + 300 + 4×60 = 1080 分钟，增加 240 分钟。
- SEMPORNA 停留 6 夜、3960 有效分钟；KL 停留 5 夜、3180 有效分钟。
- B = 1080/60 + 3×2 = 24；本例只有海岛权重，KL 不增加 E，E 仍为 100；综合分 50.603448。

费用变低、负担变高，两条见证互有取舍。这只说明两条已知行程之间不存在单方全优，不构成全局 Pareto 完整性证明。

### B03：长中转

返程报价从 10/14 00:30 起飞到 10/15 06:00 抵达，历时 29.5 小时。加首程 6 小时和两端接驳 2 小时，共 37.5 小时。夜间飞行 1+5=6 小时。

B = 37.5 + 2×3 + 1.5×2 + 6 = 52.5，综合分 45.015213。该行程符合请求约束，不能仅因“很累”而宣称不可行；由指标与未来推荐规则表达取舍。

### B06：双重停留不足

10/03 15:00 到达，10/05 09:00 离开，日期差 2 夜；有效分钟为 300+720+60=1080。因此预期同时包含 `stay_nights` 和 `usable_minutes`，不能为了通过测试只保留一个错误。

## 验证工具与报告

- `load_dataset`：结构、ID、外键、时区、航段连接、价格/行李口径、参数检查。
- `validate_request`：输入范围、目录/日期覆盖和版本支持检查。
- `evaluate_witness`：给定一个报价/访问序列，重新计算约束与分项指标，不选择下一站。
- `run_scenario`：比较手工预期与实际复核值，检查显式差值及充分无解证据。
- `run_suite`：检查内容锁，按场景 ID 稳定顺序运行。`--scenario` 只限定执行场景，仍检查整套数据锁。

报告中的 `future_search_status` 是为 M2 保存的预期，不是 M1 搜索结果。两个无解证据分别只扫描首程报价价格、是否存在返程报价；没有路径枚举。

`expected.metrics` 可以是显式选定字段的子集，列表长度必须一致；`valid` 和完整错误集合必须一致。真实复核指标完整输出，即便某些指标没有手工断言。不能据未断言字段的存在声称其已被独立验证。

## 可复现性

- 所有输入为固定 JSON，无随机数、当前时间、网络报价或自动数据生成。
- 内容锁使用排序对象键、UTF-8、紧凑分隔符的规范化 JSON SHA-256；数组顺序仍有意义。换行风格不改变锁。
- tzdata==2024.2 从包资源直接读取，不使用操作系统时区数据库。
- 评分用 40 位 Decimal 中间精度、ROUND_HALF_UP 六位结果；参数版本固定。
- 报告没有墙钟时间、绝对路径和性能数字；相同输入连续 CLI 运行可字节级比较。
- 环境复现范围：已实测 Windows + Python 3.12.1；其他系统运行步骤已列出，尚未实测。

## 修改基准的规则

1. 先说明产品假设或数据规则为什么需要改变，并更新 PRD/ADR（如适用）。
2. 手工核对报价、时刻与预期；不要把校验器输出当作唯一的预期来源。
3. 修改数据时提升 dataset_version；修改评分语义时提升 scoring_version 并明确实现支持；基准语义改变时提升 benchmark_version。
4. 使用 `benchmark_tools.run.canonical_digest(read_json(path))` 逐文件计算审核后的新值，显式修改 fixtures.lock.json。运行器没有自动刷新锁或预期的选项。
5. 执行完整场景与测试，核对文档中的数量、指标和未决假设状态。

内容锁用于发现意外修改，不是防恶意篡改的签名。数据与预期一起被不当改写仍可能互相吻合，因此手工推导和评审仍必需。

## M1 验收与 M2 交接

已执行：`py -3.12 -m unittest discover -s tests -v`，30 项通过，内含全部 20 个产品场景、错误数据注入、错误无解证明拒绝、预期/数据改动检测，以及两次独立 CLI 的 JSON 比较。

运行 M2：py -3.12 -m benchmark_tools.run_m2。它会先检查 M1 预期，再把请求与报价子集交给搜索器，比较完整可行集和独立 oracle 的完整 Pareto 集。参见 [M2 验收报告](m2-results.md) 及 [机器结果](../benchmarks/m2-results.json)。
