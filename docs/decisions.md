# 架构决策记录（ADR）

状态：包含 M0–M9-001 的已接受决策；历史阶段选择保留，取代关系见新增条目。  
最后更新：2026-09-22

本文件保留决策背景与代价。已接受表示方案获批准，不表示已经实施。小项目先用单文件；决策较多、查找困难时再拆到独立目录，不预设复杂流程。

## ADR 模板

```text
ADR-NNN：标题
日期：YYYY-MM-DD
状态：提议 / 已接受 / 已取代
背景：需要解决什么问题，受什么限制
决策：具体采用什么
替代方案：考虑过什么及未采用原因
收益与代价：获得什么，承担什么限制
重新评估条件：什么证据出现时重审
关联文档：需求、架构、模型或算法链接
取代关系：如适用，记录新旧 ADR 编号
```

已接受条目不因后续改进被抹去；新决策通过新 ADR 取代旧条目，修正错字可直接编辑。当前状态以本文件为准，具体实现细节以相关规格文档为准。

## ADR-001：使用确定性优化生成路线

- 日期：2026-09-15
- 状态：已接受
- 背景：联合选择目的地、顺序、日期与停留，需要满足预算、时间及必去约束，并能审计与复现。
- 决策：以显式报价图、约束检查、评分函数和多目标搜索生成路线。第一版不使用 LLM。
- 替代方案：LLM 直接编排行程难以保证引用真实边和满足约束；纯手工路线模板限制发现能力。模板仅用于结果解释。
- 收益与代价：可验证、可复现、可计算取舍；需要自行维护结构化数据和校准评分，不能天然理解任意自然语言。
- 重新评估条件：若后续证明自然语言输入有价值，可增加偏好解析或解释层；路线可行性仍由确定性内核负责，改变此原则须用户明确决策。
- 关联文档：[PRD FR-03–05](product/prd.md)、[算法](algorithm.md)。

## ADR-002：先用模拟数据验证算法

- 日期：2026-09-15
- 状态：已接受
- 背景：需要可控的反例与正确性基准，真实价格波动不利于稳定复现。
- 决策：M1–M2 使用版本化、固定的模拟日期级报价；M4 用少量人工采集报价评估真实参考价值。
- 替代方案：全量真实数据成本高且难控制边界；纯随机报价可能制造不具代表性的优势。采用人工设计案例和明确来源标记。
- 收益与代价：能验证时间约束、Pareto 筛选和非直觉组合；不能据此证明真实省钱、覆盖率或预订可用性。
- 重新评估条件：核心正确性通过后，开始人工采样；若模拟数据与人工样本的结构差异影响结论，修订测试集并重新测量。
- 关联文档：[问题简报](product/problem-brief.md)、[数据模型](data-model.md)。

## ADR-003：先做本地单体原型

- 日期：2026-09-15
- 状态：已接受
- 背景：首要风险是推荐是否有价值，而不是多用户服务能力。
- 决策：Python 单体、CSV/JSON、内存索引；先结构化文件输入输出，M3 再加本地表单。
- 替代方案：独立 Web 前端、API、数据库、队列和云部署增加维护面，当前没有对应验证需求。
- 收益与代价：搭建和调试简单，便于检查数据与算法；不提供远程访问、多用户并发或持久业务账户。
- 重新评估条件：用户试用证明价值，并明确需要远程共享、并发或持久存储时再评估部署与存储架构。
- 关联文档：[架构](architecture.md)、[PRD 里程碑](product/prd.md)。

## ADR-004：首期不接实时航班 API

- 日期：2026-09-15
- 状态：已接受
- 背景：外部接口引入覆盖、权限、费用、延迟、限流和报价口径工作，会分散概念验证资源。
- 决策：首期不接实时 API 或抓取。人工数据通过统一报价模型导入；保留来源、采集时间和覆盖清单，不先造通用连接器框架。
- 替代方案：立即接入一个或多个实时供应商，可以改善新鲜度，但不能自动解决路线价值、数据一致性和查询组合数量问题。
- 收益与代价：把投入集中在联合优化与用户选择；输出只有估计参考价值，无法承诺当前可购买价格。
- 重新评估条件：M4 出现明确用户价值，且人工更新成为主要瓶颈；届时评估覆盖、价格口径、调用成本和可复核性后另作决策。
- 关联文档：[架构数据流](architecture.md)、[PRD 非目标](product/prd.md)。

## ADR-005：M1 使用手工见证、隔离报价子集与内容锁

- 日期：2026-09-15
- 状态：已接受（M1 实施选择，遵循用户“不实现优化器”的约束）
- 背景：需要验证产品假设和数据正确性，但不能提前实现搜索器，也不能由同一个算法自动生成所有预期。
- 决策：固定 JSON 数据；场景显式限定报价子集；人工列出见证行程、指标和差值；无解仅采用可直接验证的充分证据。运行器只读，所有样本和场景用规范化 JSON SHA-256 锁定。固定 Python 3.12、tzdata==2024.2，直接读取包内时区规则。
- 替代方案：随机生成价格缺少可解释性；共享全部报价会导致案例相互污染；实现穷举 oracle 会跨入用户尚未授权的搜索阶段；依赖系统时区版本会影响复现。
- 收益与代价：基准独立于未来优化器，错误数据和预期漂移可被发现；只验证已列出的路径，不能证明可行集/Pareto 全集。增加一个小型时区数据依赖。
- 重新评估条件：M2 获授权后另建独立穷举与搜索器对照；M3 扩规模时新增性能基准，不让 M1 手工见证充当完整候选空间。
- 关联文档：[M1 基准](benchmarks.md)、[数据模型](data-model.md)、[架构](architecture.md)。

## ADR-006：M2 以完整 DFS 和独立穷举建立正确性基准

- 日期：2026-09-16
- 状态：已接受（M2 实施选择，遵循用户“正确性优先、不优化性能”）
- 背景：M1 见证不足以证明发现能力或集合完整性，需在不引入性能复杂度的前提下完成优化核心。
- 决策：生产核心用不可变状态、稳定顺序 DFS、硬约束校验、独立评分和 O(R²) 两两 Pareto 比较。测试 oracle 用目的地排列与报价笛卡尔积，再调用保留的 M1 见证检查器。搜索器不读取已知答案。
- 替代方案：直接把见证当候选无法验证路线发现；让 oracle 调用生产搜索或评分会掩盖共同错误；先上复杂剪枝会增加漏解风险。
- 收益与代价：完整可行集、指标和 Pareto 集可交叉校验；全量保留路线、重复扫描报价和两两比较随规模增加会很慢。两套验证共享输入规则和固定时区数据，不能证明源数据真实。
- 具体简化：不存储未使用的部分状态评分；扫描全部出境报价推导停留夜数，不建日期索引。墙钟耗时字段为 null，保证报告可复现；M3 再增加实际性能测量。
- 重新评估条件：M3 获授权且有代表性规模测量后，才考虑索引、剪枝或近似搜索；每次变更必须保持本次精确基准或明确近似质量。
- 关联文档：[算法](algorithm.md)、[M2 结果](m2-results.md)、[架构](architecture.md)。
- 取代关系：不取代 ADR-005；M1 的见证与锁仍保留，M2 增加实际搜索和完整 oracle。

## ADR-007：M3-001 使用 Streamlit 构建本地交互原型

- 日期：2026-09-16
- 状态：已接受
- 背景：需要尽快验证用户能否理解结构化输入、推荐卡和路线取舍，不需要生产级前后端。
- 决策：使用 Streamlit 1.44.1 作为薄展示层。UI 通过纯适配函数构造现有 TripRequest，并直接调用 travel_core.search；演示配置以 JSON 固定报价子集。
- 替代方案：独立 React/API 会引入部署和接口工作；命令行/原始 JSON 不适合理解性测试。
- 收益与代价：单进程本地启动、开发和试用简单；视觉定制、深链接、并发和部署能力有限，Streamlit 引入额外前端运行依赖。
- 重新评估条件：用户试用证明价值，且出现远程分享、多用户并发、精细交互或独立发布需求。
- 关联文档：[演示指南](demo.md)、[M3 结果](m3-results.md)、[架构](architecture.md)。

## ADR-008：M3-002 使用 Community Cloud 与下载式 Pilot 记录

- 日期：2026-09-16
- 状态：已接受
- 背景：5–8 名参与者需要通过链接使用同一原型并留下结构化记录，但当前不需要账户、数据库或生产运维。
- 决策：保持 Streamlit 单体，准备由 GitHub 仓库部署到 Streamlit Community Cloud。每次任务在浏览器会话内生成匿名 `pilot-record-v1` JSON，由参与者下载并交给主持人；产品遥测与主观反馈使用不同顶层对象。
- 替代方案：本机屏幕共享限制异步参与；第三方分析或数据库引入个人信息、凭证和运维；邮件/自由文本无法稳定关联实际展示方案。
- 收益与代价：无 secrets、部署面小、记录可检查；依赖参与者下载文件，刷新会丢失未下载内容，无法形成自动漏斗或并发持久分析。
- 重新评估条件：Pilot 证明价值且人工收集成为主要瓶颈，或需要持续多人试用时，再评估最小服务端存储与同意机制。
- 关联文档：[Pilot 指标](pilot-metrics.md)、[用户测试手册](user-testing.md)、[M3-002 结果](m3-002-results.md)。

## ADR-009：M5 使用隔离的确定性生成目录和外部测量器

- 日期：2026-09-16
- 状态：已接受
- 背景：需要从玩具 fixture 扩展到 30–50 个目的地并测量性能，同时不能污染 M1 内容锁、修改 M2 oracle 或提前优化算法。
- 决策：以无随机源的生成器产出并提交 `data/m5`；全部记录显式标为模拟。性能案例从同一目录选择嵌套报价子图，测量器在 `search()` 外记录时间和 `tracemalloc` 峰值，并用结果摘要核对计时/内存两次运行一致。
- 替代方案：手写数千条 JSON 难以复核；随机图不利于重复；直接扩写 M1 会破坏独立正确性基线；在测量前加入剪枝无法获得现状基准。
- 收益与代价：目录可重建、规模变量可解释、优化器语义不变；合成拓扑和单次墙钟测量不能代表真实供应商数据或所有机器。
- 重新评估条件：接入人工/真实报价后比较分支度、日期密度和连接结构；算法改动后用相同案例和 M2 oracle 复测。
- 关联文档：[M5 数据扩展](m5-data-expansion.md)、[M5 性能报告](m5-performance-report.md)、[算法](algorithm.md)。

## ADR-010：M6 将决策解释与目的地描述留在展示层

- 日期：2026-09-16
- 状态：已接受
- 背景：用户需要理解价格、体验、交通负担和新增目的地的取舍，同时不能让说明文案成为隐藏优化输入。
- 决策：解释只使用 `SearchResult` 中的确定性指标和本轮展示方案间差值；目的地类型、活动、季节说明和交通难度放在独立的 `data/m6` 描述目录。界面把描述信息与参与优化的停留、季节系数和接驳分钟明确分区。
- 替代方案：把描述性标签直接加入评分会改变 M2 语义；用 LLM 自由生成理由难以复核数值和声明边界；在数据目录重复推荐停留值会造成来源漂移。
- 收益与代价：解释可追溯，优化器保持不变；文字模板和模拟描述的表达能力有限，且相对差值只代表本轮展示候选。
- 重新评估条件：用户研究显示模板无法支持决策，或引入经过验证的真实描述数据；任何影响路线排序的新字段必须另行修改数据模型、算法和正确性基准。
- 关联文档：[M6 场景库](m6-scenarios.md)、[M6 演示流程](m6-demo-flow.md)、[架构](architecture.md)。

## ADR-011：LLM 只承担受约束的输入理解

- 日期：2026-09-17
- 状态：已接受
- 背景：结构化表单不足以体现用户从模糊意图开始的真实体验，但路线正确性与可复现性不能交给语言模型。
- 决策：LLM 只使用当前目录生成的严格 JSON Schema 提取旅行条件；不提供航班报价、搜索工具或路线输出能力。结果通过本地白名单和既有 TripRequest 校验，并由用户确认后才调用确定性优化器。手动模式始终可用。
- 替代方案：让模型直接生成行程会绕过报价图和约束；纯规则文本解析难以覆盖自然表达；强制所有用户使用 AI 会让 API 故障阻断产品。
- 收益与代价：自然语言体验与核心正确性边界分离；语义提取仍可能不稳定，需要显示假设、未解析内容和人工确认，并引入一个外部模型依赖。
- 重新评估条件：真实用户验证显示自然语言输入没有学习价值，或提取错误无法通过确认流程有效控制；不得因此把路线生成移入 LLM。
- 关联文档：[M7 AI 决策原型](m7-ai-decision-prototype.md)、[M7 部署](m7-deployment.md)、[架构](architecture.md)。

## ADR-012：M9 共用核心的 Streamlit 与 Vercel Web 演示

- 日期：2026-09-22
- 状态：已接受，部署验收以 README 实际状态为准
- 背景：用户明确要求进入开发阶段，交付可向 OTA、面试官公开演示的完整产品，并授权 GitHub/Vercel 发布。历史本地交互与验证资产需要保留。
- 决策：保留 Streamlit，增加同源 FastAPI 与静态 HTML/CSS/JavaScript 产品界面；两个入口复用 Python 请求校验、`travel_core` 与解释组件。Web 通过根目录 `server.py` 与 `vercel.json` 部署，不建立独立优化服务、数据库或前端构建工程。模型密钥只在服务端环境配置，客户端不接触凭据。
- 替代方案：只交付文档或截图不能满足可操作产品目标；把 Streamlit WebSocket 服务直接作为 Vercel 函数不适合当前运行形态；重写优化器或增加独立前后端业务服务会增加一致性维护成本。
- 收益与代价：可以通过公开链接演示完整旅程，同时保留历史测试；两种界面需要分别验证交互。每实例限流不等于全局配额，公开演示不等于生产容量承诺。
- 重新评估条件：实际使用证明需要持久会话、可靠全局配额、更高并发或细分服务边界时，按新的需求另行决策。
- 关联文档：[架构](architecture.md)、[产品案例研究](m9-case-study.md)、[M9 演示流程](m9-demo-flow.md)。
- 取代关系：取代 ADR-003/007/008 中仅采用本地或 Community Cloud 分享的当前交付限制；保留这些决策在原里程碑的历史有效性及 Streamlit 运行、下载式反馈设计。

## ADR-013：M9 可空意图草稿与强制人工确认独立版本化

- 日期：2026-09-22
- 状态：已接受；语义可靠性尚未独立验收
- 背景：M8 冻结 v1 评估判定为 C，缺失、歧义和语义偏移不能由 schema 合法性证明已解决。产品需要可编辑的草稿阶段，并保持历史评估可复现。
- 决策：新增 `travel_product.intent` 的 `m9-intent-v2`，不改动 `travel_ui/natural_language.py`、M8 corpus/prompt/schema/评分器或历史结果。必要机场、日期、天数、预算缺失时保留 null；未说明年份不迁移到演示年份。明示可编辑默认值、假设与未解决内容，由用户补全和明确确认后生成 TripRequest，再运行现有校验与搜索。服务端默认使用 DeepSeek `deepseek-flash`，手动与固定示例始终可用。
- 替代方案：为了形成完整请求自动填满必要字段会制造确定性；原地修改 v1 会破坏历史评估；让模型直接搜索或放宽约束违反核心边界。
- 收益与代价：未知信息可见、确认流程可测试，历史基线不变；用户仍可能漏掉错误。组件测试和单次成功演示不能证明准确率、Pilot 准入或产品价值。
- 重新评估条件：用独立开发集迭代后，在未消费 holdout 或新增独立集执行预设可靠性验收；真实用户研究再验证确认机制是否有效。
- 关联文档：[M9 意图契约](m9-intent-contract.md)、[M8 结果](m8-results.md)、[PRD A-12/A-13](product/prd.md)。
- 取代关系：保留 ADR-011 的 LLM 只理解输入原则；新产品路径把“直接生成完整请求”细化为“草稿→确认→请求”，v1 继续用于冻结评估与兼容入口。

## ADR-014：版本化提供者接口与描述/优化数据分离

- 日期：2026-09-22
- 状态：已接受
- 背景：产品需要清晰的目的地资料和数据来源，同时为后续可靠库存留下接入位置；本轮没有商业航班 API 授权范围，也不能修改固定算法基准。
- 决策：通过 Python `FlightProvider` / `DestinationProvider` 协议实现本地模拟适配。航班查询返回原报价、CNY 整数分、来源和固定采样时间；40份描述单独存于 `data/m9`，停留、偏好及月份数值复用原 Dataset。所有描述与报价携带模拟标识、版本、更新时间和 `simulated_unverified` 状态。公开搜索仍固定使用 M6 的18个目的地、264条报价。
- 替代方案：直接接实时库存增加覆盖与口径风险；复制停留数值导致漂移；在展示文案中加入隐藏评分会改变算法语义；通用插件平台超出当前所需。
- 收益与代价：资料与价格的来源、时间和覆盖可解释，接口便于后续替换；模拟描述和季节月份未经现实验证，40个资料地点不等于40个可搜索地点。
- 重新评估条件：有可靠且授权的真实样本时，先规范化为版本化 Dataset 并通过现有校验，再验证提供者和比较行为；搜索过程中不得动态取价。
- 关联文档：[M9 提供者](m9-providers.md)、[架构](architecture.md)、[PRD FR-15](product/prd.md)。
- 取代关系：延续 ADR-002/004 的模拟数据与不接实时航班原则，以及 ADR-010 的描述分离；新增轻量接口和完整资料目录，不取代原正确性基准。
